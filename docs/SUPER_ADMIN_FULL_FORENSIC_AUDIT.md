## Evidence and root cause of the screenshot

`Django apps/admin_portal/views.py:1391` counts AnalyticsEvent rows for total_events and the five interaction counters, but lead_submissions comes from actual Lead rows. `Django apps/leads/views/patient_views.py:184` creates a lead_submitted event after a saved lead and catches event-write failures. Repository-wide Flutter searches found no analytics ingestion client, event route constant or runtime emitter. Therefore the app can create real leads/server events while recording no other app interactions.

The offline probe deliberately seeds seven synthetic leads/events: GET admin/analytics returns exactly 7,0,0,0,0,0,7. It also executes a real local lead POST: 201, Lead count and server event count each increment once. This explains a **possible source mechanism**, not the provenance of the owner's seven rows. Other builds/imports/admin writes may exist in production. Correlate deployed build/commit, sanitized ingestion counts, raw-event/Lead reconciliation and exact Dubai date bounds before asserting the physical numbers are correct.
