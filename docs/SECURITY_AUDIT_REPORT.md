# Application security and privacy review

Review date: 2026-10-20. Repository: `majd-khalifa/AestheticWay`.

## Baseline and scope

This security branch, `codex/application-security-privacy-hardening`, starts at the verified visual recovery integration commit `a535ac703b9538f0ede2a139b9879f92be750edd`. It preserves the Clinic Portal, Super Admin, Windows image resolution and Patient Portal work. The recovered design, VIP/Featured carousel, image decoding assertions and visual golden files are retained. PR #6 is not merged by this work. The security PR is intended to be stacked on its visual recovery branch until that dependency is merged.

The review covers Flutter authentication and profile workflows, all three role portals, API repositories and their object identifiers, networking, error handling, storage/cache lifecycle, media selection/upload/rendering, links/referrals/maps, privileged actions, dependencies, Android/iOS configuration and reachable Git text history. Django was inspected in the supplied `backend-latest-reference` snapshot; the older `audit/backend` reference was retained. No Django file, production setting, credential or patient record was changed.

Methods: source inspection, repository-wide searches, synthetic unit/widget tests, mock HTTP adapters, dependency metadata checks, lockfile verification and local history scanning. OWASP MASVS/MASTG and API Security Top 10 are review frameworks, not a certification. No authorized staging URL or five-role fixture set was supplied. There was no production API probing, enumeration, brute force, load test or genuine patient-data extraction. Public package metadata queries are dependency checks, not application penetration tests.

## Finding classifications

- **Confirmed vulnerability:** a privacy/security failure reproduced in a controlled local fixture.
- **Confirmed weakness:** an unsafe source path or configuration is established; deployed exploitability is not established.
- **Potential risk requiring backend verification:** deployment or product policy must be checked before concluding vulnerability.
- **Not reproducible:** the examined source/fixture does not support the alleged failure; this is not a universal assurance.
- **Accepted/documented residual risk:** a limitation or retained behavior with an explicit owner/next verification step. This label does not imply the business has formally accepted it.

Severity reflects potential impact in this platform, without an unsubstantiated CVSS score. Source-confirmed backend findings remain unverified on the live deployment.

## Authentication, transport and storage details

Access/refresh credentials remain in platform-backed FlutterSecureStorage. They are not moved to ordinary preferences. Secure persistence ordering is retained; cached user maps cannot be mutated by callers. Storage exceptions still result in best-effort in-memory operation: native keystore failure/relaunch behavior requires device testing and must not be presented as successful durable persistence.

Logout invalidates local credentials and presentation state before awaiting network. Best-effort refresh revocation and device deactivation use captured old credentials, a separate no-refresh Dio and short timeouts; completion cannot erase a later login. Offline logout cannot invalidate an already issued server access token. Refresh rotation/blacklisting exist in Django, but account-wide revocation remains server work. Existing concurrent refresh tests include 500 synthetic requests with one refresh, stale refresh protection, retried multipart data and rejection without inappropriate logout on a retried validation error. This is a bounded mock regression, not a live load test.

Every ApiClient call stamps its session before asynchronous interceptor scheduling. Successful and failed late responses are cancelled on an epoch change. Auth/profile methods also check the identity snapshot because tests/fakes and asynchronous secure-storage writes can bypass or outlive Dio. Media preparation checks the original session before issuing its eventual write. The root rebuilds navigation only at identity/role boundaries, preserving the recovered UI during normal profile refresh.

The API must be configured with an HTTPS base URL; credentials cannot leave that configured origin/port/prefix. Alternate HTTPS staging bases remain an explicit build/configuration choice, not a runtime redirect fallback. CDN images use unauthenticated providers; media URL query signatures are preserved and are not logged. No certificate-validation bypass was found. Certificate pinning was deliberately not added without an owner, backup pins and a rotation/outage plan. Android/iOS release-device TLS and redirect behavior must still be verified against the deployed edge.

## Inputs, links and private presentation

Phone entry retains the unified LTR, digits-only country selector and international E.164 normalization. This is not proof that a number is owned; OTP and backend validation remain necessary. Account contact-change flows retain backend verification. Backend text renders through Flutter Text rather than a WebView/HTML interpreter. Arabic/medical Unicode is not stripped; identifiers/phone/email retain LTR presentation. Server length limits and Unicode confusable/bidi policy require validation at trust boundaries rather than destructive name rewriting.

Google destinations are parsed using the existing strict host/coordinate validator. Legacy MapsLauncher wrappers now route through that validator and encode place IDs/search strings as query values instead of interpolating executable URL structure. Spoofed `google.com.attacker` links are rejected. Contact launch failures no longer print phone numbers or WhatsApp message URLs. Links intentionally handed to an external app can enter that app's history; inquiry notes/JWTs are never added automatically. No arbitrary backend URL fetching was introduced.

Referral display/share accepts the unified `https://aestheticway.ae/invite/<token>` form and rejects userinfo, other hosts, ports and unexpected structure. No native verified inbound app-link handler/Android intent filter was found; end-to-end web invite attribution and iOS/Android domain association remain deployment work. Do not claim native referral attribution is verified. No manual registration referral input or coupon UI was added.

Super Admin lead lists already omit patient phone numbers; readonly detail may show contact information under the existing permission. Masking temporary passwords reduces casual exposure but does not create reauthentication. Credential copy stays explicit; clipboard/history/keyboard/screenshot risks and expiry require product/native/server decisions. No device-wide screenshot blocking was added without a workflow requirement. All new fixtures use synthetic names, phone numbers, tokens and notes; screenshots/goldens were not replaced with real records.

## Dependency, build and history checks

- `dart pub outdated --json --show-all`: 117 resolved Dart packages, no current advisory flags and no retracted packages reported. `flutter_secure_storage_macos` and `js` are reported discontinued; plan supported migrations with platform tests. Package metadata cannot prove the absence of vulnerabilities.
- `flutter pub get --offline --enforce-lockfile`: successful; SHA-256 of `pubspec.lock` unchanged. No dependency upgrade is hidden in this frontend change.
- Backend PyPI review: 26 exact requirements pins checked; five packages returned advisory metadata. The sanitized snapshot [backend_dependency_advisories.json](security/backend_dependency_advisories.json) records GHSA/CVE aliases and fixes. Latest-index versions are review candidates, not approved production upgrades. OSV's separate API was unavailable; advisories came from PyPI's public version metadata. Reachability, installed versions and native dependencies are not covered by this check.
- Local `tool/security_history_scan.py` examines UTF-8 reachable Git blobs up to 4 MiB for private-key, provider-token and JWT shapes without printing matched values. The pre-security-commit scan examined 915 text blobs and found no shape matches. Binary files, unreachable objects, nonstandard secrets and external CI secret stores are outside this heuristic. No history was rewritten and no credential was tested against a provider.
- Android source uses only the launcher-exported activity required for startup; no new exported IPC handler or WebView was added. Cleartext and backup policy are explicit. Release signing uses four CI secret variable names and cannot fall back to debug signing. No signing material is committed. Android native Gradle/signing, iOS archive/keychain/backup and real-device permission behavior were not executed in this Linux environment.

## Business-rule preservation

No payments, cart, checkout, scheduling calendar, home-service flow or regulatory identity UI was added. Products remain cosmetic brand showcases without prices or purchase/contact actions. Media stays Camera/Gallery based through LuxuryImagePickerField; no URL text field was introduced. Phones remain unified. Referral UI remains invite links and milestones. Role portals remain separate; Super Admin supervision remains readonly. The exact lead confirmation remains `تم إرسال طلبك وستتواصل العيادة معك`. Patient visual recovery and VIP/Featured priority tests remain part of the final suite.

## Residual risks and release requirements

1. Ali must deploy/test B01–B08; source changes in this PR cannot enforce Django permissions, rate limits or revocation.
2. Run the five-role staging matrix in [SECURITY_REGRESSION_TEST_MATRIX.md](SECURITY_REGRESSION_TEST_MATRIX.md), including direct forged requests that bypass Flutter. Mock tests are not evidence of deployed BOLA prevention.
3. Verify API edge HTTPS/redirect/proxy/header/body limits, storage ACLs, signed URL expiry, ffprobe, backup exclusion and native release signing. Production settings source already has DEBUG false, HSTS, secure cookies and restricted CORS; the deployed values were not inspected.
4. Confirm temporary-credential expiry/forced change, Admin step-up/MFA policy, authorized supervision data minimization, access logging and retention. These are not invented frontend capabilities.
5. Media preflight is shallow. EXIF stripping, malicious-content processing and safe private-media delivery require server controls. Public showcase media and patient profile images need separate documented ACL/retention policies.
6. Repeat dependency scanning in CI and arrange an independent authorized penetration test after backend deployment. This review neither eliminates all vulnerabilities nor certifies the platform secure.
