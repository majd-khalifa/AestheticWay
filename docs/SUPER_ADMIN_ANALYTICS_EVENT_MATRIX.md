## Complete call-site ownership

- Home clinic carousel/cards, Clinics Directory, Nearby and search: shared clinic-profile navigation prevents counting both tap and detail as two views. A Maps action on the nearest branch must retain its clinic/branch context without transmitting the coordinates in analytics.
- Clinic profile: two direct external-link call sites and shared contact sheet must use the same future typed clinic-contact adapter; do not patch only a generic launcher that lacks tenant identity.
- Offers: inspect the actual contact destination. Lead CTA produces only the saved backend lead. No product-specific call/WhatsApp or shopping actions are added.
- My Requests: both expanded/detail and card contact buttons are legitimate clinic-context sources; no patient/reference/notes go to analytics. Existing operational IDs stay in authorized API contracts, not telemetry metadata.
- Profile support, referrals share, Clinic Portal staff contact, Google Business linking/admin map inspection: not patient clinic engagement; exclude from the clinic series. If role-wide operational usage is later wanted, use separate approved definitions.
- Current launchers swallow launch failure into bool; future adapter must preserve immediate loading/failure feedback and count attempts truthfully, not successful real-world outcomes.

## Ownership and state

Use the already existing event-type spellings: app_open, clinic_view, whatsapp_tap, call_tap, maps_tap. **Do not post to a guessed route.** Existing analytics/events is source-confirmed, but its current payload lacks an idempotent key/ACK and accepts unsafe events. Client wiring is explicitly deferred, not silently treated as verified collection.

Proposed client: typed enum/context only, opaque random event UUID, no stable device/contact identifier, bounded in-memory queue (50, TTL 15 minutes), no disk persistence, no body logging, discard on logout/account switch, captured SessionSnapshot before dispatch and ACK handling. Coalesce duplicate in-flight UI actions; a real later action gets a new UUID. One app-open per authenticated activation; one profile view per visible route. Await neither queue nor network before the UI action.

Proposed retries: only after server UUID uniqueness is implemented and independently tested. At most 3 attempts with bounded exponential full jitter and Retry-After handling; same event ID/body for all attempts. Retry network/429/5xx only when session and TTL remain valid. Do not replay 401 across accounts, retry 403/validation errors, or manufacture success after an ambiguous ACK. Current legacy API has no such guarantee, so no production retry/emission loop was introduced.

Coverage: server must report collection state/version/start date per metric/build, unavailable reason and data-retention bounds. A valid returned 0 is a recorded count; an absent/uninstrumented metric is unavailable, not a proved business zero. Unique authenticated accounts must be a separate server metric, never a label for event counts or registered accounts.
