## Confirmed fixes and retained behavior

- Android app ID stays `com.aestheticway.aesthetic_way`. Flutter3.41.5 Gradle extension actually declares API36 and min24; explicit reviewed compile/target pins prevent an incidental SDK change. Gradle8.14 distribution now has its official SHA256 checksum. AGP8.11.1, Kotlin2.2.20, Java17 compatibility and NDK28.2.13676358 are retained.
- Signing uses only `AW_ANDROID_STORE_FILE`, `AW_ANDROID_STORE_PASSWORD`, `AW_ANDROID_KEY_ALIAS`, `AW_ANDROID_KEY_PASSWORD`. Missing/partial settings or a nonexistent file reject a release. `printReleaseConfiguration` reports resolved DSL values and a boolean, without credential paths/values. Owner workflow is manual, restricted to main and the `android-release` environment; it never publishes.
- Android release manifest retains INTERNET, HTTPS-only networking, disabled backup and existing external-app visibility; only `mailto` visibility is added. Final **merged** permissions and debuggable/API values come from actual AAB evidence. No broad storage, location, microphone or advertising permission is added.
- iOS existing Bundle ID stays `com.aestheticway.aestheticWay`, minimum iOS13, Swift5 mode, iPhone/iPad families1,2 and UIScene AppDelegate/SceneDelegate. SDK26 is a build SDK requirement, not a reason to make the minimum OS26. Debug/Profile/Release now have appropriate Pods xcconfigs. No team ID is fabricated.
- The approved logo replaces native iOS 1×1 launch placeholders in a fixed 128pt aspect-fit frame; existing light native canvas remains. Patient screens/artwork are not redesigned.
- Camera/Photos purpose text is localized in EN/AR; video is selected from Gallery, so microphone permission is not requested. Image/video picker cancellation and decoded image source priority retain prior tests/logic. All four resolved iOS plugins supply their own privacy manifests; CI inventories actually packaged manifests. The app manifest declares observed data categories and no cross-app tracking. Final App Store privacy answers still require backend/operator review.
- Secure storage remains device-only unlocked Keychain for JWTs, ordered token writes, role-bound session epochs and explicit logout. Default Keychain group is now explicit in all iOS configurations. Keychain may survive uninstall; no destructive blanket purge was added. A reinstall with retained choices is not an empty first install. Empty storage still defaults English/Light.
- Public legal links are discoverable from registration and each role's existing account/settings area. Deletion requests require confirmation and open email only after the user's tap, without auto-inserting names, phone numbers, JWTs or credentials; failure/duplicate taps/unmounted navigation are handled. The full server deletion gap stays P0. Support response aliases now match the verified Django `support_*` keys.
- Patient success/history/detail no longer paint or announce operational request references. IDs, parser fields, API confirmations, status refresh and authorized Clinic/Super Admin references remain intact. Detail API calls require a UUID, not a reference/path fragment. This presentation preference does not replace server object authorization.
- A confirmed client-side recovery bug was fixed: a lead-specific429 no longer globally blocks My Requests GET. Repeated lead writes still honor Retry-After; global read429 and service503 protection remains. Patient parsing also discards unexpected staff-only notes before constructing the model.

## Updated backend and consultation contract

The newly attached `AESTHETIC_WAY_BACKEND_SOURCE_d1023b0.zip` is the read-only authority. Its 393-file hash inventory is kept outside this Flutter repository. Twelve files changed/new against ca15dc6; the accounts API/legal routes, patient serializers and patient object filters are unchanged. No Django file is copied into this PR or modified.

- Latest `LeadCreationThrottle` has isolated `lead_create` scope, 20/hour, alongside global user throttling. Duplicate consultation comparison includes clinic, patient, branch and practitioner; it uses a 15-second window and emits `Retry-After: 15`. Save failures release the cache lock. These are **implemented in supplied source**, not newly verified live deployment.
- POST `/api/v1/leads/` accepts JSON clinic/branch/practitioner/treatment/offer/product UUIDs, lead_type, service_name, patient_name, patient_phone, optional patient_email/notes, empty preferred_time_window and consent_accepted. Patient identity is server-derived. No calendar or scheduling input is added.
- Successful response retains `success`, `lead_reference`, `confirmation_message`, `created_at`; there is no returned lead UUID in this create response. History supplies real UUIDs. Flutter retains the reference internally and does not fabricate a UUID from it or display it to patients. The mandatory Arabic success text remains **تم إرسال طلبك وستتواصل العيادة معك**.
- GET `/api/v1/leads/my/?page=1&page_size=20&status=...`, count and UUID detail routes are preserved. Patient serializer excludes internal notes/history/moderation. Both UUID detail aliases use `Lead.objects.filter(patient=request.user)` and IsAuthenticated/IsPatient. Source inspection found **no cross-patient IDOR** in those routes. Reference strings are not a public lookup route. Black-box two-patient tests require isolated credentials and are not claimed performed here. `IsPatient` also permits super_admin; patient endpoints still scope records to that administrator's own user, but this role exception should be reviewed against strict portal isolation.
- d1023b0 also clears stale Google aggregates when Place ID is removed and invalidates clinic/Home snapshots. Flutter's existing truthful Place-ID gating stays unchanged; no stale ca15dc6 limitation or live-delivery claim is carried forward.
